## 二、关键决策：是否迁到 Vite/Next.js？

### 选项对比

| 方案 | 工作量 | 风险 | 推荐 |
|---|---|---|---|
| **保留 in-browser Babel 模式** | 0 | 低（直接对接） | ✅ **推荐** |
| 迁到 Vite + React | 1.5 天 | 中（路径/import 改造） | ❌ 不推荐 |
| 迁到 Next.js | 3 天 | 高（SSR/路由完全重构） | ❌ 不推荐 |

### 选"保留"的 5 个理由

1. **演示场景**：评委只看 UI 效果，不看 webpack 配置
2. **部署成本最低**：`python -m http.server 8000` 或 nginx 静态托管即可
3. **避免改造引入 bug**：4 人 7 天没时间踩坑
4. **生产化是 V1 的事**：决赛后再迁不迟
5. **后端解耦**：前端只需把 mock data 替换为 fetch 调用

> **决策**：保留现有架构，新增 `api.js` 做后端对接，env 切换 mock/real 模式。

## 三、对接策略（前后端契约）

### 3.1 总体架构

```
┌──────────────────────────────────────────────┐
│ 前端（设计稿，零改造）                         │
│ HTML + JSX(Babel) + tokens.css                │
└─────────────────┬────────────────────────────┘
                  │
            window.TT_API = {
              chatStream(question, mode, sessionId),
              listDatasets(),
              getCitation(messageId),
              uploadFile(file),
              runBatchEval(jsonl),
              ...
            }
                  │
                  ↓ fetch / SSE
┌──────────────────────────────────────────────┐
│ 后端 FastAPI                                  │
│ /api/chat/stream  (SSE)                       │
│ /api/datasets     (REST)                      │
│ /api/citation/:id (REST)                      │
│ /api/upload       (multipart)                 │
│ /api/eval/run     (multipart + SSE)           │
│ /api/eval/download/:type                      │
└──────────────────────────────────────────────┘
                  │
                  ↓
┌──────────────────────────────────────────────┐
│ Agent + LLM + Sandbox + DuckDB                │
└──────────────────────────────────────────────┘
```

### 3.2 SSE 事件协议（与设计稿 14 步 trace 完美匹配）

后端推送，前端 chat.jsx 替换 mock setInterval 即可：

```jsonl
{"type":"trace_step","i":1,"name":"接收用户问题","group":"感知","detail":"...","status":"running","badge":null}
{"type":"trace_step","i":1,"status":"done","duration_ms":12}
{"type":"trace_step","i":2,"name":"加载可用能力","group":"感知","detail":"工具集 8 项","status":"running"}
{"type":"trace_step","i":2,"status":"done","duration_ms":28}
...
{"type":"answer_chunk","mode":"business","text":"华南区"}
{"type":"answer_chunk","mode":"business","text":"Q1 同比下滑..."}
{"type":"chart","kind":"bars","title":"...","data":[...]}
{"type":"chart","kind":"line","title":"...","data":[...]}
{"type":"insight","kind":"异常下跌","text":"...","severity":"high"}
{"type":"citation","datasets":["..."],"columns":[...],"sql":"...","sample":[...]}
{"type":"followups","mode":"business","items":["...","..."]}
{"type":"done","message_id":"m_123","total_ms":3140}
```

**关键设计点**：
- `trace_step` 先 `running` 再 `done` 两次推送，前端实现"待办→完成"动画
- `answer_chunk` 流式逐 token，匹配设计稿 typewriter 效果
- 一条消息可推送多个 `chart` / `insight`
- `citation` 一次性推送（包含 SQL + 样例数据）
- `followups` 区分双模式

### 3.3 数据结构对齐（直接复用 data.js 字段）

设计稿 `data.js` 的结构本身就是良好 API 设计：

| 前端字段 | 后端响应字段 | 说明 |
|---|---|---|
| `conv.question` | `message.content` (role=user) | 用户问题 |
| `conv.bizText / expertText` | `message.answer.business / expert` | 双模式答案 |
| `conv.charts[]` | `message.charts[]` | 图表数组 |
| `conv.insights[]` | `message.insights[]` | 异常洞察 |
| `conv.bizFollowups / expertFollowups` | `message.followups.business / expert` | 追问建议 |
| `D.citation` | `message.citation` | 引用溯源 |
| `D.traceSteps[]` | SSE 流推 | 14 步 trace |

→ **后端按这套字段返回，前端零适配。**
