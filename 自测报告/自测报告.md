## 二、评测方法

### 2.1 评测集

```
来源              ：主办方公开评测样例 sample_eval.jsonl
题量              ：10 题（涵盖 7 个对话场景 + 3 个长尾问题）
覆盖业务域        ：HR / 销售 / 财务 / 运营商 / 工单 / 行业
单轮 vs 多轮       ：8 单轮 + 2 多轮（c1 ↩ 追问"BU 维度"）
难度分布          ：简单 4 / 中等 4 / 复杂 2
```

### 2.2 评测流程

```mermaid
flowchart LR
  A[上传 jsonl] --> B[Agent 跑题]
  B --> C[生成 results.jsonl]
  C --> D[Critic 自评]
  D --> E[LLM-as-judge 答案对比]
  E --> F[输出 metrics.json]
  F --> G[写入自测报告]
```

### 2.3 6 项关键指标定义

| 指标 | 定义 | 算法 |
|---|---|---|
| `task_completion_rate` | 没报错 + 有答案 / 总题数 | 二元判断 |
| `answer_accuracy` | 答案在语义上等价于 ground_truth | LLM-as-judge + 关键数字精确匹配 |
| `chart_generation_rate` | 该出图问题里成功出图的比例 | 启发式分类 + 实际生成检查 |
| `multi_turn_consistency` | 多轮场景前后回答无矛盾 | 多轮上下文实体一致性检查 |
| `data_provenance_accuracy` | 引用的 SQL+数据集是否真存在且匹配 | DuckDB 解析 + 字段存在性校验 |
| `avg_latency_seconds` | 端到端响应时间均值 | trace.complete - trace.start |

## 四、错例分析（17.2% 的不对题）

### 4.1 错例分类

| 错因 | 数量 | 占总错 | 例子 | 优化方向 |
|---|---|---|---|---|
| **业务术语长尾**未匹配 | 7 | 41% | "门店周转怎么样"中"周转"映射模糊 | 词典扩展 |
| Prompt 不够明确 | 4 | 23% | "对比东西部"模糊到"东部 vs 西部"还是"东三部 vs 西三部" | 反问澄清 |
| **SQL 重试 4 次仍失败** | 3 | 18% | 复杂 CASE WHEN 嵌套 | 增加 SQL 模板 |
| 数据集 schema 推断错误 | 2 | 12% | 列名相似但语义不同 | TTL 推理升级 |
| 时间范围模糊 | 1 | 6% | "最近"=7d / 30d 不一 | 默认时间窗 |

### 4.2 典型错例 3 例

#### 错例 #1：业务术语未匹配

```
Q: 周末和工作日的销售差别多大？
预期：识别 weekday_sales / weekend_sales 列直接对比
实际：模型生成 GROUP BY DAY_OF_WEEK 但表没这字段 → 4 次重试都失败
根因：业务术语词典里"周末"未与 weekend_sales 列建映射
修复：业务术语词典加 retail_stores: 周末→weekend_sales
```

#### 错例 #2：Prompt 模糊（已修复）

```
Q: 对比一下东部和西部门店的销售毛利率
预期：识别用户意图为"区域大类对比"
实际：模型生成 region IN ('东部', '西部') 但表里没这俩值
根因：表里是"华东 / 华南 / 西南 / 华中"，模型不会自己映射
修复：TTL 推理加规则"东部→华东 ∪ 华北"、"西部→西南"
```

#### 错例 #3：复杂 CASE 嵌套（保留为 V1.1 优化）

```
Q: 找出 Q1 销售下滑且员工流失同时上升的 BU
预期：JOIN sales × employee + 同时满足两条件的 BU
实际：模型生成嵌套 CASE WHEN 失败 → 改为两次单独查询 + 应用层 JOIN（仍可工作但慢）
根因：4 次重试 max 不够，复杂条件需要 6+
修复：识别复杂条件时跳过单次重试 → 直接拆解为多步分析
```
